# 118,688,898,254 tokens — where it comes from

Written to be doubted. Every figure below is reproducible from this repository,
and the places the number is *weak* are marked as such.

## The number

| machine | floor |
|---|---:|
| macbook-air-m1 | 55,281,972,031 |
| hp-laptop-linux | 32,406,338,482 |
| dell-latitude-7480-linux | 30,530,206,673 |
| asus-laptop-linux | 423,110,994 |
| dell-inspiron-desktop-linux | 47,270,074 |
| **total, 5 of 6 machines** | **118,688,898,254** |

Still on disk today: **46,488,455,959**. The difference —
**72,200,442,295, or 60.8%** — is work whose transcripts have already been
deleted.

## Why there is a gap at all

Claude Code deletes session files after `cleanupPeriodDays`. In `cli.js`,
`PM7()` → `Ay0()` compares `statSync(path).mtime` against a cutoff and calls
**`unlinkSync`** — a hard delete, no archive, no tombstone. Keyed on *mtime*,
which is why a copied profile survives its own retention window.

But the tool also keeps `stats-cache.json`, a **frozen lifetime counter** that
is not reduced when transcripts are removed. So after a sweep the disk holds a
fraction of the sessions and a counter that still remembers all of them.

## How the floor is computed

```
floor = frozen counter  +  transcripts whose timestamps postdate lastComputedDate
```

**Concatenated, never subtracted.** The two windows overlap and neither
contains the other, so subtracting would remove real usage and adding blindly
would double-count the overlap. Taking the counter plus only the transcripts
that come *after* the counter's own high-water mark is the largest figure that
cannot double-count. It is a **floor**: the true number is higher, not lower.

Per-account, not per-machine. Folding profiles into their account *before*
applying the counter moved this machine from 30.9 B to 81.0 B, and the fleet
from 66.5 B to 166.2 B in an earlier pass — because one counter per account was
being credited once per machine.

## Why it is not inflated

**Global uuid dedup.** Discovery is by *shape* — any directory containing
`projects/**.jsonl` — which is what finds profiles a glob misses (four under
`~/Desktop` alone, worth 817,889,443 tokens). Wide discovery is only safe with
dedup: message uuids are deduplicated across every profile, so a copied
directory contributes nothing twice. Without it two scanners disagreed by
37.2 B vs 11.4 B; with it they agree.

**Two independent implementations agree.** On the merged corpus, `standout` and
`starforge` — different authors, different languages, no shared code — both
report 16,800 sessions, 97 active days, 1,533.4 hours, 188,465,919 input tokens
and 17,449,275,636 cache reads. They differ by 41,511 output tokens, **0.07%**.

**Counters, not estimates.** Every figure is a sum of the four `usage` fields
the provider's own API returned — `input_tokens`, `cache_creation_input_tokens`,
`cache_read_input_tokens`, `output_tokens`. Nothing is modelled or extrapolated.

## What the number is NOT

**It is not 118 billion tokens of writing.** 94.5% is `cache_read` — the
conversation being re-sent on every turn. Real, billed, and not new text.

| | tokens | share |
|---|---:|---:|
| re-read from cache | 43,941,932,070 | 94.5% |
| written to cache | 1,952,221,429 | 4.2% |
| sent fresh | 406,573,197 | 0.9% |
| generated by the model | 187,729,263 | 0.4% |

**New content is 2,546,523,889 tokens.** The first version of the stats page
compared the billed total to books as though it were distinct prose and
overstated it by 22×. Any comparison to a corpus of writing has to use the
2.5 B, not the 118 B.

**It is five machines, not six.** A Dell Latitude 7480 running Windows has
never been scanned.

**It is usage, not cost.** No dollar figure appears anywhere in this repository,
deliberately: the same model costs differently through different routes, and
prices change under a number that does not.

## Reproducing it

```bash
python3 run.py rebuild     # deletes every derived file, recomputes from machine folders
python3 test_scanner.py    # 28 assertions, each a bug that shipped once
python3 check_consistency.py
```

The scanner is versioned; `run.py status` prints which version produced each
machine's numbers, so a stale scan cannot quietly sit inside a fresh total.
